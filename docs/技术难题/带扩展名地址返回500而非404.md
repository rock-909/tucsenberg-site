# 带扩展名的不存在地址返回 500 而非 404

**发现时间**: 2026-07-25（整改 Wave 5 移除废弃图片后的预览验证）
**状态**: **已修复** — 2026-07-25
**影响面**: 所有不存在的、路径里带点的地址

## 现象

生产构建下访问任何不存在的带扩展名地址，返回的是 `500 Internal Server Error`，
而不是应有的 `404 Not Found`：

```text
/random.txt              → 500
/does-not-exist.svg      → 500
/next.svg                → 500   （Wave 5 移除后）
/nope                    → 404   （不带点的地址正常）
```

Wave 5 移除的五张废弃图片里，`/images/*` 四个走 `public/` 静态目录仍返回 404，
只有根目录的 `/next.svg` 落进这个坑。

这是主干上早就存在的问题，不是 Wave 5 引入的（在 `a1af99b` 上同样复现）。

## 根因（修复时更正过一次）

**最初的判断是错的。** 本文档最早写的是"没有根级 404 页，Next 找不到兜底页只能抛错"，
并据此把修法定为打开 Next 的 `experimental.globalNotFound` 实验开关。

实测服务端日志推翻了这个判断：

```text
⨯ Error: Unknown locale: random.txt
    at Module.O [as generateMetadata]
```

真实链路是：

1. `src/middleware.ts` 的 matcher 为 `/((?!api|_next|.*\..*).*)`，
   **带点的路径被排除**，拿不到 locale 改写。
2. 这类请求原样落到 `[locale]` 动态段上，Next 把 `random.txt` 当作 locale 取值。
3. `[locale]/layout.tsx` 里其实有 `if (!isLocale(locale)) notFound()` 的校验，
   但**元数据生成先于布局渲染执行**，`getLocalizedPath()` 拿到非法 locale 直接
   `throw new Error("Unknown locale: ...")`，于是变成 500。

也就是说：不是"没有兜底页"，而是**非法的 locale 取值被放进了路由，代码在校验之前
就抛异常**。

按实验开关那条路走过一遍，加了 `globalNotFound` 与对应的全局 404 页面文件
后重新构建，`/random.txt` 仍然是 500——因为请求根本没走到"找不到路由"那一步，
而是在元数据生成里就炸了。该方案已弃用，试验文件移入废纸篓，仓库中不保留。

## 修法

`src/app/[locale]/layout-metadata.ts`——把布局里已经有的那句校验，搬到最早的入口：

```ts
const { locale } = await params;
if (!isLocale(locale)) {
  notFound();
}
```

布局里本来就写着 `if (!isLocale(locale)) notFound()`，它没起作用只是因为**元数据
生成先于布局渲染执行**。同一句校验放进 `generateLocaleMetadata`，非法 locale 走
正常的 404 兜底，而不是抛异常变成 500。治的是"代码在校验之前就抛异常"这个根因，
不新增页面、样式、字体或文案。

### 走过一遍又退回来的方案：`dynamicParams = false`

修复当天先用的是布局段配置 `export const dynamicParams = false`，它确实把
`/random.txt` 变成了 404。但它是**路由层的一刀切**：不在 `generateStaticParams`
返回值里的取值一律拒掉，而 `src/app/[locale]/[...rest]/page.tsx` 这个 catch-all
恰恰是靠"任意路径都能进来"才能把访客送进品牌 404 页的。段配置会向下级联，catch-all
被一起关掉，于是 `/this-page-does-not-exist` 这类**不带点**的普通错误地址，从品牌
404 页退化成了 Next 自带的白底 "This page could not be found."——没有回首页的出口，
没有导航，没有品牌。

当时没人发现，是因为守这条的 `tests/e2e/not-found-recovery.spec.ts` 属于"哪个 CI
车道都没跑"的三个用例文件之一（见 `docs/技术难题/门禁断言审查2026-07-24/`）。打开
全量 E2E 后它当场就红了。

`cacheComponents` 目前为 `false`；`dynamicParams` 这条路线已经退回，将来若重新
启用 Cache Components 也不再牵涉它。

## 已知边界：带点的地址进不了品牌 404 页

改法只解决 500→404，带点的地址拿到的仍是框架自带的兜底页。这是结构决定的：品牌
404 页住在 `[locale]` 段里，渲染它本身就需要一个合法 locale，而 `random.txt` 正是
那个非法值。要让这类地址也进品牌页，得加一层根级 layout + not-found，代价远大于
收益——真人打错的路径不带点，带点的基本只有爬虫和旧资源链接。

## 防回归

`tests/e2e/not-found-status.spec.ts` 断言六个不存在的地址（含带点与不带点两类）
全部返回 404，同时断言真实存在的资产仍返回 200。

`tests/e2e/not-found-recovery.spec.ts` 守渲染结果：不带点的错误地址必须落到品牌
404 页（`main` 里有 "404"、"Page not found"、"Back to homepage" 三样），带点的
地址断言状态码 404 加框架兜底页——把上面那条已知边界写成断言，将来谁改动这一带，
是修好了还是又退化了，都会当场显形。

## 验证

```bash
APP_ENV=production pnpm build
pnpm exec playwright test tests/e2e/not-found-status.spec.ts
```

回归检查（修复后实测）：首页、产品列表、询价页、联系页、关于页、产品详情页、
`sitemap.xml`、`robots.txt`、`/api/health` 全部 200；退役的 `/zh` 仍 404；
`/en/about` 仍 307 重定向到无前缀地址。
