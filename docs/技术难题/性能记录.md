# 性能记录

这里记录长期有用的性能结论。旧逐轮 Lighthouse 数字只说明当时的 starter/profile
状态，不是当前 Tucsenberg launch proof。当前上线证明以
`../项目基础/上线验证.md`、`../项目基础/发布验证.md` 和
`../项目基础/验证等级.md` 为准。

## 当前口径

- Lighthouse 是手动性能证明，不属于默认 CI、git hook 或 `pnpm release:verify`。
- 运行入口是 `pnpm website:lighthouse`；它会单独构建到 `.next-lighthouse`，再用
  4173 端口测量，避免复用普通 `.next` 或 3000 端口上的外部服务。
- `CI_DAILY=true` 时测当前 16 个 canonical public route：主页、Products、OEM、
  两个 guides、About、Request Quote、Contact、Warranty、Privacy、Terms、5 个产品页。
- 每个 URL 跑 3 次，断言使用 optimistic 聚合。当前硬门：performance >= 0.78、
  LCP <= 4500ms、TBT <= 350ms、FCP <= 2000ms、CLS <= 0.15、Speed Index <= 3000ms。
- `total-byte-weight <= 490000` 仍是 warning 级黄债信号，不是 release 阻断。
- 产品详情页不跑 Lighthouse SEO category gate；共享性能、a11y、best-practices 和字节预算仍适用。

## 历史时间线

- 2026-05-24：starter 阶段多轮 Lighthouse 黄债治理确认 `total-byte-weight`、
  `resource-summary.transferSize` 和 `network-requests.transferSize` 才是网络口径；
  treemap `resourceBytes` 只能辅助归因，不能当节省数字。
- 2026-05-24：首屏 motion 边界实验保留结论是“LCP-critical 文本不要依赖初始隐藏的
  client motion”；不要把这个外推成“删除所有 motion”。
- 2026-05-24：prefetch 策略、产品详情负载、shared payload 实验都证明过：
  一次只改一个变量，Contact、产品详情、列表页不能混成同一个原因。
- 2026-05-26：SEO/JSON-LD 带来的 payload 被保留；不能为了 Lighthouse 数字删除
  业务内容、SEO、a11y、i18n 或视觉体验。
- 2026-06-21/22：全量 starter 性能审计没有 P1；唯一有证据的 P2 候选是全局
  render-blocking CSS floor，必须作为 UI-foundation/CSS split spike 处理。
- 2026-07：当前整库审查把性能问题改按 Tucsenberg 口径记账：首页 motion 运行时成本、
  `/contact` 动态化来源、Worker 包内 zod/env 校验图谱重复，以及 Radix/CSS/motion
  等候选都只能用 fresh build + fresh Lighthouse 重新证明。

## 仍有效结论

- 旧 `/zh`、旧 blog、旧 `/en/products/north-america` 数据已退役，只可追溯，不可引用为当前。
- shared payload 类收益优先级高，但必须保护表单、SEO、a11y、i18n、motion 和内容。
- CSS / UI foundation 可能是大头，但牵动组件治理，必须单独开 lane。
- Lighthouse warning 不能靠放宽阈值“修复”；先找资源归因，再决定 keep / revert。
- 性能实验方法见 `性能实验优化方法论.md`；当前技术栈和 Next.js 行为见
  `../项目基础/技术栈.md`。
