## 4. 本轮 12 条发现

严重度分布：**P0 = 0，P1 = 1，P2 = 7，P3 = 4**。

完整的证据、根因、修复建议与反证记录在 `02-findings.json`。下面是给非技术读者的说明。

### P1（建议上线前处理）

**`FPH-2607-001` 你在配置里写的「PDF 不要被搜索引擎收录」和「图片缓存一年」，在真实网站上一条都没生效。**

两件事和你以为的不一样：

- 五份产品规格书 PDF 本来设了不让 Google 收录。实际上线后这个设置不会生效，PDF 可能直接出现在搜索结果里。买家点进去看到的是一份没有询盘按钮的 PDF，而不是能下单的产品页。
- 公司 logo、社交分享图和全部 PDF 本来设了缓存一年，实际每次访问都重新下载一遍。页面更慢，Cloudflare 流量费更高。

原因是这些文件在 Cloudflare 上由另一套机制直接发出，根本不经过网站程序，所以写在程序配置里的规则对它们无效。在本地用另一种方式跑的时候规则是生效的，所以之前一直看不出来。

修法很小：把这两条规则搬到 Cloudflare 认的那个文件里就行。

## 5. 加权深挖结果

### 5.3 类型质量（合约未明确认领，本轮补做）

`pnpm type-check` 通过只说明能编译。本轮单独查了四类逃逸：

- **`any`**：生产代码 **0 处**。
- **`@ts-expect-error` / `@ts-ignore`**：生产代码 **0 处**（仅 6 处测试与 2 处 e2e，都带说明）。
- **非空断言（`!`）**：生产代码 6 处，逐条核验**全部可证安全**——`String.split` 至少返回一个元素、`resend!` 前有 `isConfigured` 守卫、`gaMeasurementId!` 前有存在判断。

**结论：类型质量在同类项目里属于优秀水平。** 唯一的成规模问题不是危险，而是同一件事有两种写法。

### 5.4 惯例一致性（合约未明确认领，本轮补做）

新代码总体与既有写法一致：组件全部具名导出（0 处 `export default`）、Props 全部用 `interface`（72 : 1）、导入路径统一走 `@/` 别名、客户端边界一律下推到叶子组件。

## 6. 证明边界：本轮证明不了什么

这一节请务必读完。全绿不等于可以对外宣布上线。

**已证明**：代码能编译、能构建、能在 Cloudflare 运行时正确响应、能扛住并发、页面内容与事实源一致、安全边界在正确方向失败。

**未证明，且本轮无法证明**：

| 事项 | 为什么证不了 | 需要什么才能证 |
| --- | --- | --- |
| 真实域名下的一切表现 | 生产域名仍是占位符 `example.invalid`（R'12 业主延期项） | 业主确定并绑定正式域名 |
| 真实 Turnstile 验证 | 需要 Cloudflare 账号侧配置 | Cloudflare 控制台凭据 |
| 真实邮件送达 | 需要 Resend 账号 | Resend 凭据 + 一次真实发信 |
| 真实表格写入 | 需要 Airtable 账号 | Airtable 凭据 + 一次真实写入 |
| **业主真的收到了那封邮件** | 这是六种证据等级里最高的一级，只有你本人能确认 | 你亲自查收件箱并确认 |
| 部署后的并发表现 | 未做真实部署 | 一次精确 SHA 的 Cloudflare 部署 + 复测 |
| 搜索表现（收录、排名） | 需要 Search Console / CrUX | 业主授权的账号 |
| 生产配置门 | 本地缺全部生产密钥，运行即失败（这是**正确行为**，不是缺陷） | 在 CI 或生产环境带密钥运行 |

**特别提醒**：`FPH-2607-001` 说的 PDF 收录问题，本轮是在本地 Cloudflare 运行时上实测的。机制与真实 Cloudflare 完全相同（同一份产物、同一个 `_headers` 文件），但严格说，真实部署后的复测仍待做。

## 8. 被否决的候选（附反证）

本轮共评估 20 个候选，否决 8 个。列出主要几条，说明否决理由：

| 候选 | 否决理由 |
| --- | --- |
| Cloudflare 并发仍会卡死（沿用上轮 P1） | 133 次并发请求全部 200，最慢 0.38 秒。无法复现 |
| 限流存储挂掉会放行（fail-open） | 询盘预设是 `failureMode: "closed"`，实测返回 503。方向正确 |
| `withRateLimit` 的降级分支是死代码 | csp 预设用的正是 `"open"`，两条分支都在真实使用 |
| 换邮件服务商成本过高，应加抽象层 | 调用方只用业务形状方法，第三方语义没越界。加层反而制造多余抽象 |
| `--border` 对比度只有 1.22:1，不达标 | WCAG 1.4.11 只要求「识别控件所必需」的非文字元素达 3:1。`--border` 用于装饰性分隔与卡片描边，表单控件用的是 `--input`（4.30–4.58:1，达标）。不构成违规 |

## 12. 需要你拍板的事

只有一件是必须你来决定的：

**`FPH-2607-008`：产品页的文案，到底该待在代码常量文件里，还是该搬进翻译文件？**

- 现状：约 1000 行英文产品文案在 `src/constants/tucsenberg-product-page-*.ts` 里。
- 一份文件（`CLAUDE.md` / `AGENTS.md`）说：用户能看到的文案一律走翻译 key。
- 另一份文件（内容 ADR，状态已接受）说：这些文件就是「产品真相」的合法归属层。
- 我的建议：**保持现状，改文档**。产品规格与文案在这里是可审阅、可 diff、可 review 的；搬进翻译文件是一次大工程，而站点目前只出英文，收益为零。只要在根指令文件的 i18n 约束后补一句例外说明就行。
