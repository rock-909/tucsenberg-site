# 修复建议排序 2026-07-26

本轮**没有修改任何业务代码**。这份文档是给未来某一轮修复用的施工顺序，是否开修由业主决定。

原则：delete-first、simplify-first。能删的先删，删不掉的再简化，都不行才新增。

## 批次 2：删掉半成品安全文件（一个小 PR）

| 编号 | 改什么 | Linus Gate |
| --- | --- | --- |
| `FPH-2607-003` | 删除 `public/security-policy.txt`；`.well-known/security.txt` 成为唯一安全联系真相 | **Delete** |

**最小改动面**

```text
public/security-policy.txt                       删除（移入废纸篓，不用 rm）
public/.well-known/security.txt                  Preferred-Languages 去掉已退役的 zh
tests/unit/content-page-placeholders.test.ts     从 PUBLIC_LEGAL_AND_SECURITY_FILES 移除该路径
tests/architecture/public-asset-surface.test.ts  从 NON_REFERENCED_SURFACES 移除该项
docs/项目基础/技术栈.md、替换边界.md              去掉对该文件的引用
```

**为什么是删而不是填**：`.well-known/security.txt` 是 RFC 9116 的标准位置，工具与研究者只认它，且它已经填了真实邮箱。保留第二份人类可读版本只会让「安全联系方式」这件事有两个所有者——正是本条的根因。

**验收命令**

```bash
pnpm test
pnpm build && pnpm website:build:cf
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8787/security-policy.txt   # 期望 404
curl -s http://127.0.0.1:8787/.well-known/security.txt                                # 期望含 sales@，不含 zh
```

## 批次 3：询盘链路上的两个「没人告诉你」（一个 PR）

| 编号 | 改什么 | Linus Gate |

| `FPH-2607-004` | 让 Turnstile 救援行的显示条件覆盖「表单已就绪但拿不到令牌」 | Keep |
| `FPH-2607-005` | 在 Airtable 记录上写一列 `ownerEmailed` | Keep |

**`FPH-2607-004` 最小改动面**

不新增组件、不新增文案键——两者都已存在（`TurnstileRescueLine` 与 `inquiry.form.turnstile.rescue*`）。只改触发条件：

```text

src/components/forms/inquiry-form-status.tsx  needsRescue 或「已就绪 N 秒仍无令牌」时渲染救援行
```

超时阈值建议 15 秒（Turnstile 正常挑战通常 1–3 秒）。

**`FPH-2607-005` 最小改动面**

```text
src/lib/lead-pipeline/process-lead.ts      createProductLeadRecord 接收 emailSent，写入记录
src/lib/airtable/service-internal/lead-records.ts  新增 ownerEmailed 字段映射
```

**注意执行顺序**：目前两条通道是 `Promise.all` 并行发出的，`createProductLeadRecord` 拿不到 `emailSent`。最省事的做法不是改成串行（会拖慢买家等待），而是并行照旧、拿到两个结果后对 Airtable 记录补一次更新；或者接受「先写记录再补字段」的两步写。**这一步要先想清楚再动手**，别为了加一列把并行改成串行。

**验收命令**

```bash

# 新增：mock Resend 失败 + Airtable 成功，断言记录含 ownerEmailed=false 且接口仍 200
# 新增 e2e：拦截 challenges.cloudflare.com 使其失败，断言页面出现带 mailto 的救援行

```

## 不建议做的事

审查过程中评估过、明确**不建议**动的：

| 想法 | 为什么不做 |
| --- | --- |
| 给邮件服务加一层 `EmailService` 接口 / DTO / mapper | 只有一个供应商、一个调用方，调用方用的已是业务形状方法。加层是拿一个「复查触发点」换一个真实的多余抽象 |
| 把 5 个产品页常量文件拆小 | 它们是单一职责的数据文件，改动原因只有一个（该产品的事实变了）。行数不是判据 |
| 把 893 行的 `tucsenberg-site-contract.test.ts` 拆开 | 它的点名清单是与真实注册表 `toEqual` 对账的，拆开反而可能拆断对账 |
| 把并行的邮件+表格改成串行 | 会让买家多等一个网络往返，换来的只是代码顺一点 |
| 修 `--border` 的对比度 | 它是装饰性描边，WCAG 不要求。改了会让全站分隔线变重 |
| 处理开发依赖的 5 个 high 漏洞 | 不发给访客，等上游升级即可 |

## 修复轮的验收总纲

任何一批做完，最低限度跑这一串（串行，`pnpm build` 与 `pnpm website:build:cf` 绝不并行）：

```bash
pnpm type-check
pnpm lint:check
pnpm test
pnpm build
pnpm website:build:cf
```

涉及路由、响应头或部署配置的批次（批次 1、2），额外补一次本地 Cloudflare 运行时实测：

```bash
pnpm exec wrangler dev --port 8787 --local &
node scripts/starter-checks.js cf-preview-smoke --base-url http://127.0.0.1:8787 --include-api-health --rounds 3
```

涉及询盘链路的批次（批次 3），额外跑 `pnpm exec playwright test`。

**每一批都必须能说清一件事：如果这个修复被改坏，哪条检查会变红。** 说不清的，说明守卫没做到位。
