## 2. 产生最高信号的做法

### 2.1 两个运行时并跑（本轮最大收获）

同时起 `wrangler dev`（8787，部署目标）与 `pnpm start`（3100，Node 对照），用同一次构建产物。

`FPH-2607-001` 完全是这个做法逼出来的：单看任何一个运行时都得不出结论——Node 上一切正常，Cloudflare 上一切「看起来也正常」（页面都是 200）。只有把同一个 URL 的响应头并排放，才看得出 `X-Robots-Tag` 凭空消失。

**回写建议**：把「同一构建产物、两个运行时、逐项对照响应头」写进 Lane 00 的必做清单。这类差异静态读代码永远读不出来，因为代码是对的，错的是它对谁生效。

### 2.2 先跑串行基线，再做静态阅读

`type-check → lint → test → build → build:cf` 串成一条后台链，跑的 5 分钟里同步做前置阅读（业主裁决、既往报告、仓库结构）。基线结果回来时，静态阅读已经有了地图，不用等。

**回写建议**：这条已经隐含在 SKILL.md 的「Preflight first / Runtime truth early」里，但没说清可以并行。值得写明：基线命令用后台跑，前置阅读同时进行。

### 2.3 变更成本演练用「全落点普查」而不是「读架构文档」

做「加一个产品」时，用的是 `grep -rln 'flood-tube-dams'` + `grep -rln 'TB-TD'` 两个探针做全仓落点普查，而不是读 `docs/项目基础/架构树.md`。结果比文档更完整（文档没提 `content/pages/en/warranty.mdx` 也点名了产品型号），也顺带查出了对账机制的存在（`toEqual` 断言），让一个本来要报的候选被正确否决。

**回写建议**：Lane 07 的演练方法应明确写成「选一个真实实例做探针，全仓 grep 落点，再逐个判断漏改会不会报错」。「读文档估算」得出的结论既不完整也不可验证。

### 2.4 反证真的改变了两条结论

不是走过场：

- `FPH-2607-004` 原判 P1「买家彻底无路可走」。反证时逐页 curl 数邮箱出现位置，发现页脚法务行有纯文本邮箱 → 降 P2。
- `FPH-2607-010` 原判 P2「类型硬转换是潜在运行时缺陷」。反证时实测 `/invalid/contact`、`/zh`、`/nope` 全部 404 → 降 P3，改判为惯例问题。

还有 8 个候选被完全否决，其中「限流 fail-open」和「降级分支是死代码」两条，如果不去查 `RATE_LIMIT_PRESETS` 的实际取值，都会变成看起来很有说服力的假发现。

**回写建议**：合约里的「单源必须反证」不该只被理解为质量控制，它同时是**严重度校准**的手段。建议在合约里点明：反证的产出不只是「成立/不成立」，还包括「成立但没那么严重」。

## 3. 产生噪音或走了弯路的地方

### 3.1 zsh 不做变量分词，两条探针脚本白跑

`for r in $ROUTES` 在 zsh 里不会分词，第一次路由矩阵把整个字符串当成一个 URL，返回 `000`。第二次改用 bash 数组 + 写成脚本文件才对。

**回写建议**：合约里已经强调 `set -o pipefail`，应该再加一条：**多值循环写成 bash 脚本文件执行，不要在 zsh 里靠变量分词**。这类错误的危险在于它不报错，只是安静地少跑——和「清单静默变短」是同一类失败。

### 3.2 猜产品 slug 浪费了一轮探测

第一次路由矩阵里，五个产品 slug 有三个是猜的（`aluminum-flood-barriers`、`boxwall-flood-barriers`、`tube-dam-flood-barriers`），全部 404。真实 slug 是 `aluminum-flood-gates`、`flood-tube-dams`、`frp-flood-barriers`。

正确做法（第二次用的）：**先从 `/sitemap.xml` 取真实路由清单，再逐条探测**。运行时自己知道自己有哪些页面，不用猜。

**回写建议**：Lane 00 的路由探测应明确从 sitemap 或路由注册表取清单，禁止手写猜测——手写清单既会漏也会假阳。

### 3.3 「.tsx 文件里没有 JSX」的检测器是错的

写了个 grep 想找出扩展名与内容不符的文件，返回 14 个结果。抽查发现检测器把 `<div\n  className=…` 这种换行写法漏判了，绝大多数是假阳性。**该条没有进入发现**，但浪费了一轮。

**回写建议**：任何自制的「模式检测器」在产出发现之前，必须先在一个已知为真和一个已知为假的样本上验证。这次是自己抽查发现的，下次可能就写进报告了。

## 4. 合约本身的缺口（本轮补做的两项）

委托明确点出了合约没认领的两块，实际做下来确认这个判断是对的：

### 4.1 类型质量

`pnpm type-check` 通过只证明能编译。本轮单独查了四类逃逸（`any` / `@ts-*` 注释 / 非空断言 / 类型断言），结论是这个仓库的类型质量属优秀——生产代码零 `any`、零关闭类型检查的注释。

但这个结论**只有单独查过才敢说**。如果只报「type-check 通过」，读者无法区分「真的干净」和「用 `any` 铺平了」。

**回写建议**：把类型逃逸扫描写进 Lane 07 的 useful checks，并明确四个探针与判据（非空断言要逐条证明安全性，不能只报数量）。

### 4.2 惯例一致性

这块产出了 `FPH-2607-011`，价值中等但真实。更重要的是过程中发现：**判定「不一致」之前必须先确认存在规则**。

第一次判定时差点写成「67 个文件违反 `coding-standards.md` 的 PascalCase 规则」。核对上下文才发现那张表规定的是标识符命名而非文件名，`Footer.tsx` 是事实惯例的例外而非规则违反——措辞完全不同，前者是指控，后者是观察。注释语言同理：全仓无任何规则可依，所以只能报告事实并请业主定口径，不能判对错。

**回写建议**：新增一条判据——**惯例类发现必须先定位规则来源；无规则可依时只报事实与影响，不判对错，并把「定规则」列为待业主处置项**。这和硬规则 2 的精神一致：不要凭执行者的偏好制造裁决。
