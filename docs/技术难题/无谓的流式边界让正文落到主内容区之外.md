# 无谓的流式边界让正文落到主内容区之外

Date: 2026-07-25
Discovered by: 收尾 `docs/技术难题/询价页CLS布局跳动.md` 里记的"小瑕疵"时顺线摸到
Status: **已修复** — 2026-07-25

## 事实

禁用 JavaScript 打开站点，实测到三件事：

| 路由 | 现象 |
| --- | --- |
| `/privacy`、`/terms` | 主内容区**完全是空的**，只剩一排灰色骨架条 |
| 全部路由 | 整页正文在 HTML 里出现**两遍**，其中一遍在 `<main>` 外的隐藏容器里 |
| `/request-quote` | 询价表单区再多一份重复副本 |

正文在隐藏容器里的证据（脚本禁用，`/request-quote`）：

```text
div < div < div < main#main-content < body          ← 可见的那一份
div < div < div < div < div#S:0[hidden] < body      ← 隐藏的那一份
```

`div#S:0` 是 React 流式渲染的落地容器。React 把已解析的子树先写到 body
末尾的隐藏容器，再用一段内联脚本搬回原位。**没有脚本就没有这次搬运**，
所以这一份永远留在 `<main>` 外面。

## 根因

三处 `<Suspense>` 边界都没有等待对象，纯属白加：

### 1. `src/app/[locale]/layout.tsx` —— 影响全站

```tsx
<main id="main-content" className="flex-1">
  <Suspense fallback={children}>
    <PageTransition>{children}</PageTransition>
  </Suspense>
</main>
```

`fallback` 和内容里是**同一棵 `children`**，于是整页正文被渲染两次：一次作为
fallback 留在 `<main>` 里，一次作为内容流进隐藏容器。服务端做了双份渲染工作，
访客下载了双份字节。

这层边界当初是为 `PageTransition` 加的。但按安装版文档
`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-pathname.md`：

> When `cacheComponents` is enabled `usePathname` may require a `Suspense`
> boundary around it if your route has a dynamic param.

本项目 `cacheComponents: false`（见 `.claude/rules/conventions.md`），
`PageTransition` 只用 `usePathname`，**不需要任何边界**。

### 2. `src/app/[locale]/privacy/page.tsx` 与 `terms/page.tsx`

```tsx
<Suspense fallback={<PrivacyLoadingSkeleton />}>
  <PrivacyContent locale={locale} />
</Suspense>
```

这两条路由是 `●` 构建期整页预渲染（`pnpm build` 输出可见），
没有任何请求期数据要等。骨架屏永远不会真正显示给有脚本的访客，
却让无脚本访客**永久停在骨架屏上**——法务页面对无脚本访客等于不存在。

### 3. `src/app/[locale]/request-quote/page.tsx`

```tsx
<Suspense fallback={inquiryFallback}>
  <RequestQuoteInquiryForm searchParams={searchParams} ... />
</Suspense>
```

边界唯一作用是把 `await searchParams` 推迟到子组件里。
但 `searchParams` 本身就让整条路由变成 `ƒ` 动态渲染（安装版 `page.md`：
*"Using it will opt the page into dynamic rendering at request time"*），
路由已经不预渲染了，边界换不来任何东西。

**共同的成因条件**：把 `<Suspense>` 当成"加了总比不加好"的默认写法，而没有先问
"这里有什么请求期的等待需要它盖住"。三处都没有。

## 修法

三处一起去掉边界，让页面自己 `await` 出结果：

- `layout.tsx`：`<main>` 里直接渲染 `<PageTransition>{children}</PageTransition>`。
- `privacy/page.tsx`、`terms/page.tsx`：把 `*Content` 的函数体并回页面组件，
  删掉 `*LoadingSkeleton`。
- `request-quote/page.tsx`：页面里 `resolveInquiryContext(await searchParams)`，
  直接渲染 `<InquiryForm>`，与 `/contact` 的 `ContactFormWithFallback` 对齐。
  `request-quote-inquiry-form.tsx` 及其测试随之退休，`searchParams → 询价上下文`
  的四条覆盖搬进 `__tests__/page.test.tsx`。

## 效果

预渲染格局不变（`pnpm build` 前后 `●`/`ƒ` 完全一致），HTML 体积明显下降：

| 路由 | 改前 | 改后 | 降幅 |
| --- | ---: | ---: | ---: |
| `/` | 255,953 B | 193,608 B | −24.4% |
| `/products` | 140,084 B | 112,382 B | −19.8% |
| `/about` | 85,474 B | 73,833 B | −13.6% |
| `/contact` | 79,323 B | 70,221 B | −11.5% |
| `/request-quote` | 64,931 B | 59,544 B | −8.3% |

（`/request-quote` 的基线已含询价页自身的修复，相对 `main` 的实际降幅更大。）

`/privacy`、`/terms` 无脚本时从"空白 + 骨架条"变成完整法务正文。

## 防回归

`tests/e2e/no-js-html-contract.spec.ts` 的 `expectBodyRenderedOnce()`：数 `h1`
的条数与文本，要求不重复且全部落在 `#main-content` 内。它不点名任何一处边界，
**任何路由**上再出现"正文渲染两遍"或"正文跑到 `<main>` 外"都会挂。首页、
`/contact`、`/request-quote`、`/about`、`/privacy`、`/terms` 都接了这条。

同一文件的 `expectNoReservedGap()` 收紧到 `#main-content` 作用域，
`/request-quote` 也纳入覆盖（改前因为结构问题只能跳过它）。

`tests/architecture/cache-components-page-boundary.test.ts` 原来断言法务页必须
`toContain("<Suspense")`——这条门禁在钉住一个已证明有害的形状。按
`CLAUDE.md` 的 Gate Discipline（"当检查逼着代码陈述假话时，改检查而不是改陈述"）
处理：删掉这半条断言，只保留它真正的意图——法务页走 `LegalPageShell`。

**没有**反过来断言 `not.toContain("<Suspense")`。
审查时被指出这只是把一个源码文本门禁换成另一个：
它同样会被注释里的 `<Suspense` 字样误伤，也会一刀切掉将来真正有理由的边界。
"正文有没有被推迟"是渲染结果的问题，交给上面那条 E2E 回答，
它已经覆盖 `/privacy` 与 `/terms`。

## 验证时踩到的坑：量到的根本不是本站

这一节比上面的正题更值得记，因为它让性能门禁在**长达数月里可能一直在量错东西**。

### 现象

同一条命令、同一份代码，连续五次跑出四种结果：

| 次序 | 命令 | 结果 |
| --- | --- | --- |
| A | 旧命令，紧跟一次手工生产构建 | 16 条全过 |
| B | 旧命令，紧跟 `pnpm website:check` | 9 条 SEO 挂在 0.69 |
| C | 新命令（自带构建） | `/contact` 第 3 次加载被浏览器拦截 |
| D | 新命令 | **16 条全挂 0.69** |
| E | 新命令，先删掉整个构建目录 | 产物实测正确，仍挂在 `/contact` |

### 三个各自成立、叠在一起就致命的机制

1. **收录开关是构建期烧死的，事后给服务端补 `APP_ENV` 没用。**
   两层，下面那层才是致命的：
   - `src/lib/seo-metadata.ts` 按 `getRuntimeAppEnv() === "production"` 决定
     收录，静态页在 `next build` 时就把 `noindex` 写进 HTML。
   - `src/app/robots.ts` 对任何非生产构建产出 `Disallow: /`，而这个文件同样是
     构建期生成的。**服务端跑 production 也翻不了案**：动态页自己的 HTML 明明
     写着 `index, follow`，照样因为站点 robots.txt 全站禁爬而挂掉
     `is-crawlable`。这就是为什么污染一次构建，16 条路由无一幸免。

2. **`next start` 遇到端口被占直接退出，不换端口。**
   `node_modules/next/dist/server/lib/start-server.js` 的 EADDRINUSE 重试被
   `isDev` 门住，生产模式只打印 `Failed to start server` 然后 `process.exit(1)`。

3. **lhci 的服务起不来时，只警告一声然后照量不误。**
   `node_modules/@lhci/cli/src/collect/collect.js` 在等不到就绪特征时打印
   `WARNING: Timed out waiting for the server to start listening.`，
   **接着继续测量**——量的是当时占着 3000 端口的任何东西。

三条叠起来的后果：只要有别的东西占着 3000，Lighthouse 就会安静地把**别人的站点**
当成本站量一遍，报告里没有任何迹象说明量错了对象。审查时在本机实际抓到过一个：
另一个工作区（`.claude/worktrees/gate-e3-e5`）遗留的测试服务，跑的是 `preview`
环境、Next 版本都不同，16 条路由全是 `noindex`。

### 谁在往 3000 端口和 `.next` 里写

- `pnpm build` / `pnpm website:check`（结尾就是裸 `pnpm build`）——写 `.next`，
  产物带 `noindex`。
- `playwright.config.ts` 的本地 `webServer`——跑 E2E 前执行 `pnpm build && pnpm start`，
  env 里设的是 `APP_ENV: "preview"`（不是 production），所以**每跑一次 E2E
  就把构建产物换成一份 noindex 的测试版**，并占住 3000；
  `reuseExistingServer` 还会让它直接接管别人已经起好的服务。
- 同一台机器上任意其他工作区的开发/测试服务。

一次 16 页的完整测量要 20 分钟以上，上面任何一件事在这期间发生，测量就被污染。

### 修法：给测量一套独占的产物目录和端口

- `next.config.ts`：`distDir: process.env.NEXT_DIST_DIR ?? ".next"`，默认不变。
- `package.json`：
  `"website:lighthouse": "NEXT_DIST_DIR=.next-lighthouse APP_ENV=production pnpm build && lhci autorun --config=./lighthouserc.js"`
- `lighthouserc.js`：URL 基址与 `startServerCommand` 统一走 `LIGHTHOUSE_PORT = 4173`，
  服务端同样带上 `NEXT_DIST_DIR=.next-lighthouse`。
- `.gitignore`、`eslint.config.mjs`、`vitest.config.mts`、`.prettierignore`
  同步忽略 `.next-lighthouse/`（否则 eslint 会去检查构建产物，直接报几百条错）。
- `tsconfig.json`：`include` 里保留 `.next-lighthouse/types/**`，
  `exclude` 里加上 `.next-lighthouse`。两个都要，缺一不可，理由见下。
- `package.json` 的 `website:lighthouse` 开头加一道端口预检：4173 上但凡有东西在
  听就直接拒跑。理由见下一节——换端口没法根治"量到别人"。

这样测量既不共享产物目录，也不共享端口：别人重建 `.next`、别人占 3000，都影响不到它。

### 为什么还要一道端口预检：固定端口堵不死

换到 4173 只是躲开了别人常清理的 3000，并没有从机制上消除端口争用。
`localhost` 同时解析到 `::1` 和 `127.0.0.1`，两个进程可以在同一端口的不同地址族
上**同时监听**（本机实测过），谁应答取决于客户端的解析顺序。

看上去最直接的修法——把服务端和客户端一起钉到 `127.0.0.1`——**会把站点跑坏**，
实测如下：

```text
next start --hostname 127.0.0.1 --port 4173
→ 每条路由都 307 到自己，无限循环
```

响应头露出了原因：

```text
x-middleware-rewrite: http://localhost:4173/en/contact
location: /contact
```

next-intl 中间件把 `/contact` 内部重写到 `/en/contact`，但重写目标带的是
`localhost`，而服务器绑的是 `127.0.0.1`。Next 判定跨源，于是把"内部重写"降级成
"对外重定向"，转回原路径，循环。`--hostname localhost` 不会坏（只开一个
`[::1]` 套接字），但它防不住 IPv4 那侧的占用，收益接近于零。

所以不在绑定上做文章，改成开跑前先看一眼端口。实测能拦住 `next start` 自己看不见
的那种情况（占用者只监听 IPv4 时，`next start` 照样打印 `Ready`，lhci 也不会
报警）。

### tsconfig 为什么既 include 又 exclude

`next build` 会自动往 `tsconfig.json` 的 `include` 里补写自己产物目录的类型路径。
**不写进去**，它每跑一次就补一次，顺带把整个文件重新格式化（数组全展开），
每次测量都产生一堆无关 diff。

但只写 `include` 会埋个雷。
`.next-lighthouse/types/validator.ts` 会为**当时**的每条路由生成一句
`typeof import(...)`，
而 `pnpm type-check` 跑的 `next typegen` 只刷新默认的 `.next/types`。
于是删掉一条路由之后，`tsc --noEmit` 就会在这份没人更新的陈旧类型里报 `TS2307`。
pre-commit 钩子正好跑 `type-check`，结果是**删路由的那次提交被自己拦下来**。

两个一起加就没事：`include` 让 Next 认为已登记、不再改写文件，
`exclude` 让 `tsc` 根本不编译它。实测验证过——手工塞一份引用不存在路由的类型文件，
`pnpm type-check` 照常通过；再跑一次 lighthouse 构建，`tsconfig.json` 一字未动。

### 验证方式

不是"跑一遍绿了"，而是**制造原来必挂的条件**：在 Lighthouse 测量进行中，
并发跑一遍 E2E（它会重建 `.next` 并占用 3000）。

```bash
CI_DAILY=true pnpm website:lighthouse &
# 等它开始测量后
pnpm exec playwright test tests/e2e/no-js-html-contract.spec.ts
```

实测结果：E2E 7 项全过，Lighthouse 16 条路由全过、退出码 0，互不干扰。

### 两次异常的最终定因

后来把日志、会话记录和残留报告对齐，两次都查到了确切成因。**都不是端口被占。**

**D 次（16 条全挂 0.69）：两个构建同时在写 `.next`。**

| 时刻（UTC-7） | 事件 |
| --- | --- |
| 08:35:27 | 测量命令启动，开始 `APP_ENV=production pnpm build` |
| 08:35:43 | 同时执行 `git push`，pre-push 钩子跑起**裸 `pnpm build`** |
| 08:36:15 | 第一份测量报告的抓取时间——此时 `.next` 已是钩子那份 |
| 08:36:17 | push 完成 |

两次构建重叠约半分钟，后完成的（不带 `APP_ENV` 的钩子构建）赢了，
lhci 的服务就架在这份禁爬产物上。日志里没有超时警告是**应该的**——
服务本来就正常启动了，问题出在启动之前。

证据不是分数倒推，是那次上传到临时公共存储、至今仍在的 15 份报告：
每一份都明确写着 `is-crawlable: score 0`，其余加权 SEO 项全过。

> 记一个我自己犯的推理错误，免得下次重蹈：曾断言"0.69 只可能是
> `is-crawlable` 单项失败"。**不成立**——任意 4 项权重为 1 的审计同时失败得
> 0.6933，显示出来也是 0.69。分类分数不足以定位失败项，必须看报告明细。

**C、E 两次（`/contact` 被浏览器拦截）：服务器被别的进程杀了。**

| | Lighthouse 开始导航 | 有进程执行 `lsof -ti:3000 \| xargs -r kill` |
| --- | --- | --- |
| C | 14:47:01.302Z | 14:47:00.529Z（导航前 0.77 秒） |
| E | 15:52:33.367Z | 15:52:31.562Z（导航前 1.81 秒） |

来自同机另一个 AI 会话的端口清理动作（很可能就是这次调查自己开的子任务——
调查期间反复用过这条命令清 3000）。用 Lighthouse 12.6.1 做过受控复现：
测量进行中杀掉服务器，得到完全相同的 `CHROME_INTERSTITIAL_ERROR` 与
`chrome-error://chromewebdata/`。

所以和 `/contact` 这个页面无关，也和"第 24 次启动 Chrome 资源耗尽"无关——
A、B、D、F 四次都跑过远超 24 次的 Chrome 启动，本机文件描述符上限是 104 万，
差着数量级。两次都恰好落在第 8 条路由第 3 遍，纯属清理动作的时点碰巧。

搬到 4173 之所以有效，正是因为别人的清理脚本盯的是 3000。

### 遗留（本次未动）

`playwright.config.ts` 的本地 `webServer` 仍然会重建 `.next`，产出 `preview`
环境的 noindex 版本。没有把它改成 `APP_ENV=production`：那一行是**刻意**把 E2E
钉在 preview 作为证明边界，CI 侧还有测试断言这一点（`ci-preview-env.test.ts`）。
改成 production 会让本地 E2E 去证明一个并不存在的配置组合——测试用的 Turnstile
密钥加上关掉的安全响应头。属于另一次改动。

隔离之后这件事已经不影响性能测量（它写的是 `.next`、占的是 3000），
留下的影响只有一条：跑完 E2E 后 `.next` 是 noindex 的，
别拿它当生产产物看。

## 顺手清掉的负空间门禁

`tests/architecture/cache-components-page-boundary.test.ts`
原来第一条断言三个早已删除的路由文件继续不存在。
这正是 `CLAUDE.md` Gate Discipline 点名禁止的写法（"守住过去重构的负空间"）：
删除本身由 git 记录，这条门禁唯一的实际效果是将来有人正当地新增同名路由时误伤。
已删除，并在文件顶部写明为什么不再加这类断言。

同类断言在 `src/app/__tests__/sitemap.test.ts` 与
`src/app/[locale]/products/__tests__/products-page.test.tsx` 里还有若干处
（断言已退休的 URL 不出现在站点地图里）。那几处与站点地图的正向断言写在一起，
性质介于"负空间"和"站点地图内容正确"之间，本次未动。
