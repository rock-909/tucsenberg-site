# 门禁断言审查 2026-07-24（批次 E）

审查对象：`tests/architecture/` 39 个文件、6414 行，其中 302 条写死字符串的断言
（`toContain("...")` 形式），分布在 82 个用例块里。

判据来自 `AGENTS.md` 的 Gate Discipline：

> 门禁是为意图服务的启发式，不是法律。当检查逼着文档或代码陈述假话时，改检查而不是改
> 陈述。不要把时点快照钉成必须断言。新守卫要保护活的真相，不要保护过去重构留下的负空间
> （例如断言已删除的名字保持不存在）。

## 结论

302 条里：

| 类别 | 条数 | 处置 |
| --- | ---: | --- |
| 1. 真架构边界，保留 | 约 160 | 不动 |
| 2. 负空间守卫，违反 Gate Discipline | 33 | 删除或改为正向断言 |
| 3. 文档内容断言（要求某文档原样写着某句话） | 约 85 | 需业主裁决，见下 |
| 4. 文案锁（把用户可见文案冻结在测试里） | 约 12 | 改为断言事实，不断言措辞 |
| 5. 逐字重复的门禁 | 8（×2 处） | 合并 |

第 2、4、5 类是明确的缺陷，建议修。第 3 类里有一部分是业主 2026-07 明确保护的
Registry / Playbook 治理系统，不能单方面动，单列裁决。

## 类 2：负空间守卫（33 条，已逐条验证）

共同特征：断言"某个已经删掉的名字/文案/步骤保持不存在"。这类守卫保护的是过去，不是
现在。它们永远为真，因此永远不会失败，也就永远不会发现任何问题；同时它们把一次性的
重构结果变成了永久的措辞约束。

- 清单只含目录内容 —— 改为断言生成的清单里每一项都能解析到 `content/` 下的真实文件，

## 类 3：文档内容断言（约 85 条，需业主裁决）

要求某个 Markdown 文档原样包含某句话。和刚在 PR #160 里从 `AGENTS.md` / `CLAUDE.md`
移除的是同一类手段。

分布：

| 文件 | 条数 | 被断言的文档 |
| --- | ---: | --- |
| `ui-component-playbook.test.ts` | 33 | `docs/design/组件使用手册.md` |
| `email-copy-boundary.test.ts` | 10 | 三份替换指引文档 |
| `component-governance.test.ts` | 8 | 组件使用手册（与上面逐字重复） |
| `proof-lane-labels.test.ts` | 8 | 上线验证、性能记录、四份 Lighthouse 记录 |
| `ui-component-index.test.ts` | 5 | 组件索引 |
| `static-public-pages-contract.test.ts` | 5 | 静态页说明文档 |
| `message-packs-contract.test.ts` | 5 | messages README、替换顺序 |
| 其余 6 个文件 | 11 | 各自的说明文档 |

这类断言分两种，**处置不同**：

**3a. 治理契约类（业主已保护，不单方面动）**
`AGENTS.md` 写着"在获批的退役证明之前，不得删除、归档或收缩 Registry / Playbook"。
组件使用手册和组件索引的断言（41 条）属于这个系统。它们的问题是实现方式——用整句字符串
匹配，改个标点就挂——而不是意图。

建议：不删，改断言粒度。把"手册必须原样包含这 33 句话"换成"手册必须覆盖这些**主题**"
（章节标题存在、表格列齐全），措辞自由。

**3b. 纯复述类（建议删）**
其余约 44 条断言的是"文档里写了代码在做的事"。文档写错不会让网站出问题，代码写错才会；
而这些断言只检查文档，不检查代码。典型：`proof-lane-labels.test.ts:85-87` 要求四份
Lighthouse 记录各自包含 `Historical starter proof` 等三句英文原文。

## 类 4：文案锁（约 12 条）

`tucsenberg-site-contract.test.ts:796-846` 把联系页和询价页的用户可见文案冻结在测试里，
包括这样一整段：

> `**Email**: sales@tucsenberg.com — we reply within 12 hours. If the details are
> sufficient, the reply includes a quote. Otherwise, we ask only for the missing
> essentials. You'll hear from a person, not a sequence.`

改一个逗号，CI 就挂。

**意图是真的**：邮箱地址要对、承诺的回复时效要真实、不能残留 starter 占位文案。
**实现是错的**：它冻结的是措辞，不是事实。

建议改为断言事实：

- 邮箱地址等于配置里的唯一真相源（现在测试里是第二份硬编码副本，同一事实两处维护）；
- 地址等于配置里的唯一真相源（同上）；
- 承诺的回复时效在页面文案、成功提示、Turnstile 兜底三处一致（现在是各写各的硬编码）；
- 页面不含 starter 占位标记（这条保留，属于类 2 里少数值得保留的负向断言：它防的是
  新引入，不是守护旧删除）。

## 类 5：逐字重复的门禁（8 条 × 2 处）

组件使用手册断言同样 8 个字符串。两处任何一处改了，另一处就成了假门禁。

建议：`ui-component-playbook.test.ts` 保留，`component-governance.test.ts` 里删除重复段，
只留文件存在性检查。

## E1 / E2 执行结果（2026-07-24）

`toContain("...")` 断言 302 → 260。39 个架构测试文件全绿，`pnpm test` 286 文件 / 2355 条
全绿，lint 与 type-check 通过。

### 四条改成正向断言

| 原断言 | 改后 |
| --- | --- |
| CI 与 lefthook 文本里不许出现 `lighthouse` / `lhci`（5 条字符串匹配） | 解析两份 YAML，收集所有真正会执行的 `run:` 命令，断言其中没有 lighthouse。注释里提一句不再误报 |
| 三个文件不许出现 `profile-fixture` / `showcase-full` | 遍历生成清单的每一条，断言 `source` 是 `active-content`、路径在 `/content/` 下、且文件真实存在 |
| 手册"缺失包装器"段不许列 Checkbox / Select / RadioGroup / Dialog | 解析该段实际列出的包装器名，断言它们在 `src/components/ui/` 下确实还不存在 |
| `.env.example` 含 `=en` 且不含 `=en,zh`（靠一正一反凑精确） | 一条精确行匹配 `/^NEXT_PUBLIC_SUPPORTED_LOCALES=en$/m` |

四条都做了变异检验：人为制造违规后测试确实失败，改回后恢复绿色。这一步是必要的——把恒真
断言换成另一条恒真断言，等于什么也没做。

### 两处审查时的归类被推翻

- `.env.example` 的 `=en,zh` 否定断言**不是**负空间。`=en` 是 `=en,zh` 的子串，正向断言
  单独存在时形同虚设，那条否定断言正是它精确性的来源。改为一条精确行匹配，两条合一。
- `docs/design/组件使用手册.md` 的"缺失包装器"段**当前根本没有列表**，四条否定断言是对空
  内容做匹配，比审查时判断的更空洞。

E3、E4、E5 未动。E5 涉及业主保护的 Registry / Playbook 治理系统，需先裁决。
