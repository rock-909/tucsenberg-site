# Current-Only Documentation Design

**状态：** 已批准，待实施计划  
**日期：** 2026-07-29  
**范围：** 项目长期文档、设计文档、技术问题记录和 Superpowers 过程文件

## 目标

把 `docs/` 收缩成只描述当前项目真相、当前维护方法和仍然有效的长期决策的知识库。
已完成计划、审查现场、证据包、会话交接、旧样稿和可以由代码或 Git 恢复的历史内容不再
常驻工作树。

这次重构必须同时做到：

1. owner 能快速知道项目是什么、怎么维护、什么时候可以正式上线；
2. agent 能找到技术栈、运行边界、设计规则和验证入口；
3. 当前技术问题、迁移候选和未来演进不会散落在聊天或旧计划中；
4. `docs/` 不再承担 Superpowers 过程文件、审查档案或机器配置的存储职责；
5. 同一个事实只保留一个长期真相源。

## 判决原则

文件只有满足以下至少一项才有资格留在 `docs/`：

- 描述当前业务、产品、架构或设计事实；
- 给出维护者现在仍需执行的操作；
- 记录无法从代码、配置或 Git 提交本身恢复的长期决策及原因；
- 描述当前仍存在的问题、风险、迁移条件或演进选择；
- 定义正式上线、部署、故障处理或安全边界。

以下内容默认退役：

- 已完成的 spec、实施计划、审查报告、证据日志和会话交接；
- 只证明某次提交、某次命令或某个时点状态的快照；
- 已被当前代码、配置、测试或另一份文档完整表达的重复说明；
- starter 时代、旧路线、被否方案、过期样稿和已经完成的整改清单；
- 仅用于解释其他文档放在哪里的多层索引；
- 可以可靠从 `package.json`、lockfile、配置、生成输出或 Git 历史读取的清单。

退役内容不迁入新的仓库内 archive。实施时按仓库规则移到 Trash；Git 历史继续提供恢复
能力。

## 目标结构

```text
docs/
├── README.md
├── 项目.md
├── 技术栈.md
├── 架构与行为.md
├── 内容与品牌.md
├── 开发与维护.md
├── 正式上线标准.md
├── 技术问题与演进.md
├── 技术决策.md
└── design/
    ├── 设计真相.md
    ├── 设计系统.md
    ├── 组件治理.md
    ├── 页面模式.md
    └── 动效治理.md
```

长期文档总量上限为 14 个 Markdown 文件。除非出现无法合理合并的新长期职责，否则不
新增目录或文件；优先扩充现有责任文件。

## 顶层文档职责

### `docs/README.md`

只做一层入口：说明 `docs/` 的边界，并按任务指向下面八份文档和 `design/`。不保存版本
号、完成状态、文件总数或历史清单。

### `docs/项目.md`

保存当前业务目标、公开站点范围、产品线、主要用户旅程、部署平台和明确的非目标。它
回答“这个项目是什么”，不重复实现路径清单。

### `docs/技术栈.md`

完整记录当前技术栈及每一层的作用：运行时、框架、UI、内容、国际化、表单和询盘、测试、
构建、Cloudflare 部署、监控及开发工具。具体版本仍以 lockfile 和配置为准，文档只写
当前采用的技术、职责边界和查证入口。

### `docs/架构与行为.md`

合并当前架构、关键链路和必须保持的外部行为，包括：

- 页面、内容、messages 和配置的真相关系；
- locale 路由与 English-only 当前状态；
- 产品发现、PDF 下载和询盘交付链；
- Server/Client 边界、缓存和 OpenNext/Cloudflare 边界；
- 关键行为合约及其真实测试入口。

不维护可从源码目录直接读出的完整文件地图。

### `docs/内容与品牌.md`

合并品牌、内容、消息文案和 CMS 边界。只保留当前可编辑入口、内容归属规则、SEO 输入、
i18n 约束、产品事实来源和 owner 更新流程。

### `docs/开发与维护.md`

合并本地启动、常用验证、配置、部署维护、监控、故障处理、AI 协作和代码审查边界。
命令只保留维护者真实会运行的最短入口，不复制 `package.json` 的全部脚本。

CI 和门禁在这里按“作用”解释，但不得把本地检查、PR required check、部署验证和真实线上
证明混成一层。每项只说明：保护什么、什么时候运行、失败意味着什么、不能证明什么。

### `docs/正式上线标准.md`

这是唯一的公开上线判决正本。必须明确区分：

1. 本地工程验证；
2. PR CI 与合并门禁；
3. Cloudflare 构建和部署验证；
4. 公开地址运行验证；
5. owner 必须确认的业务、法务、联系信息和真实询盘回执。

每项使用可判定的通过条件、证据和责任人。普通 release proof 不能冒充正式公开上线通过。
时点 SHA、测试条数和某次成功结果不写成永久标准。

### `docs/技术问题与演进.md`

这是当前问题和未来迁移候选的唯一台账。只收录仍未解决、仍可能复发或会影响未来决策的
事项，例如：

- 当前技术难题及影响；
- 已知限制和触发条件；
- 未来迁移候选及启动条件；
- 依赖或平台变化带来的演进选择；
- 已解决但必须长期记住的根因和防复发约束。

每项至少包含：现状、影响、当前处置、重新评估条件和真相入口。已解决且规则已进入代码、
测试或其他正本文档的事项从台账移除，不保留完成日志。

实施时至少复核并保留这些仍可能影响决策的种子事实：构建命令共享 `.next` 不能并行、
Cloudflare/OpenNext 与 PPR/cacheComponents 的当前边界、PDF noindex 和静态资源 header
语义、正式上线 proof 分层、middleware 不迁 proxy 的裁决、客户端边界预算新路径、产品
文案归属冲突，以及方向 E 当前裁决中尚未完成的落地约束。它们只保留短结论和当前真相入口，
不搬运审查日志或原始证据。

### `docs/技术决策.md`

合并仍有效的架构、内容和设计决策。每项只记录：决定、原因、仍适用的边界、重新打开的
条件和当前真相入口。被替代、已完成或只对某次实施有意义的决策退役。

## `docs/design/` 结构

`docs/design/` 继续作为正式设计治理目录，但从当前 15 个文件压缩到 5 个。

### `设计真相.md`

保留当前视觉方向、品牌气质、页面层级、禁止事项和其他四份设计文档的职责边界。它是
设计入口，不再保存历史探索过程和被否样稿。

### `设计系统.md`

合并当前 `色彩系统.md`、`设计令牌.md` 和 `网格系统.md` 中仍有效的内容。CSS 和组件代码
仍是真实实现；文档解释 token 角色、使用规则、网格意图和变更同步要求。

### `组件治理.md`

吸收 `组件使用手册.md` 和 `Storybook覆盖范围.md` 中仍有效的规则。保留正式组件入口、
复用顺序、允许的变体、Storybook 责任和组件变更验证，不保留逐次盘点或空缺清单。

### `页面模式.md`

保留当前页面骨架、section、卡片、CTA、表格、表单和产品页模式。吸收两份视觉翻译文档
中已经成为当前页面规则的部分；历史探索问答和样板推导过程退役。

### `动效治理.md`

吸收 `动效原则.md` 中仍有效的原则，保留动效准入、Server/Client 边界、reduced-motion、
性能限制和验证要求。只保留当前仍被采用的剖面动画或交互资产约束。

以下设计材料在有效规则合并后退役：

- `组件使用手册.md`
- `Storybook覆盖范围.md`
- `动效原则.md`
- `网格系统.md`
- `色彩系统.md`
- `设计令牌.md`
- `视觉翻译-旗舰页样板.md`
- `视觉翻译-自顶向下设计.md`
- `可迁移设计资产-剖面动画与页脚.md`
- 两个方向 E HTML 样稿

## Superpowers 过程文件

Superpowers 当前上游默认使用 `docs/superpowers/specs/` 和
`docs/superpowers/plans/`，但该路径是可覆盖的整理约定，不是执行机制要求。本项目改用：

```text
plans/YYYY-MM-DD-<topic>-design.md
plans/YYYY-MM-DD-<topic>-plan.md
```

规则如下：

- `plans/` 只保存尚在设计、待执行或正在执行的过程文件；
- 设计和实施文件用 `-design.md`、`-plan.md` 区分，不再创建 `spec/`、`specs/` 或
  `plans/plans/`；
- 计划完成后，先把仍有效的长期结论合并进 `docs/`，再将过程文件移到 Trash；
- 不建立计划索引、状态清单、archive、README 或 `.gitkeep`；
- `.superpowers/sdd/` 和 `.superpowers/brainstorm/` 继续作为被忽略的运行期临时目录，
  不提交。
- 根 `plans/` 只归当前 Superpowers 未完成的设计和实施文件；`advisor-plans/` 等其他
  workflow 的专用目录不与它混用，也不把旧 improve 计划重新解释为当前执行顺序。

项目指令和本地 workflow 中所有硬编码的旧输出路径必须同步改为这一约定。

本设计文件、后续实施计划、support-layer 审查报告和 TSV 都是迁移过程材料，不自动成为
长期文档。收口时必须重新按本文件的判决标准审查它们；若没有不能由当前正本或 Git 历史
替代的长期事实，也一并移到 Trash。

## 非文档数据

`docs/技术难题/客户端边界预算.json` 被当前质量检查读取，属于机器消费的质量基线，不是
文档。它必须迁出 `docs/`，放到质量检查附近；同步修改读取脚本和测试后才能移除原路径。

其他 JSON、TSV、图片、原始命令输出和审查 evidence 默认不进入新 `docs/`。若某项被运行
时代码或门禁真实消费，应迁到对应代码、配置或测试目录，而不是为了保留而留在文档树。

## 引用与门禁迁移

压缩文件不能留下悬空引用。实施时必须全仓检查并同步：

- `AGENTS.md`、`CLAUDE.md`、`.claude/rules/**` 和项目本地 skills；
- `README.md`、`DESIGN.md`、`PRODUCT.md`；
- 源码注释、测试说明和其他稳定文档；
- 读取具体文档路径或断言文档内容的测试、脚本与门禁。

至少点名检查这些已知硬引用：

- `scripts/quality/checks/client-boundary.js` 与 `tests/unit/scripts/client-boundary-budget.test.ts`；
- `tests/architecture/env-example-parity.test.ts` 对部署、上线文档和环境变量说明的检查；
- `tests/architecture/ui-component-playbook.test.ts`、`src/components/ui/README.md` 和
  `DESIGN.md` 对组件治理入口的引用；
- `AGENTS.md`、`CLAUDE.md`、`.claude/rules/ui.md`、`.claude/rules/content.md` 以及本地
  behavior-driven-development skill 对文档和 Superpowers 输出路径的说明；
- 生产源码注释中指向旧设计资产或技术难题的链接。

`组件使用手册.md` 合并后，组件治理的唯一正式入口是 `docs/design/组件治理.md`；测试应
验证新入口或真实组件规则，不得为了保留旧文件名而保留旧文档。

方向 E 的 HTML 样稿可以退役，但当前视觉裁决、五项硬伤和未完成落地约束必须先进入
`docs/design/设计真相.md` 或 `docs/技术决策.md`。

门禁应保护真实行为或真实配置。仅断言某份说明文档存在、包含固定短语或维护一份重复清单
的检查应退役或改为检查其真正意图，不能为了让旧测试继续通过而保留旧文档。

## 实施方式

实施前先重新获取 `origin/main`，把实施分支同步到最新主线；若发生冲突，先解决基线
冲突再开始文档迁移。不得以旧主线上的一次性路径扫描作为最终证据。

实施分成四个可独立验证的批次：

1. 建立九份顶层正本，合并当前仍有效的内容；
2. 把 `docs/design/` 合并为五份正本；
3. 迁移机器数据、代码引用、规则指针和必要门禁；
4. 将所有剩余历史文档、审查证据和完成计划移到 Trash，并做全仓悬空引用检查。

每批都先建立新真相源并验证引用，再退役旧文件。不得先删除后凭记忆重写。

当前未跟踪的 `docs/技术难题/整库审查2026-07-26/` 也必须在第一批处理：先确认其中
是否有尚未进入当前正本的事实；没有的话按 Trash 规则退役，不能因为它未被 Git 跟踪就
绕过审查。

## 验收标准

完成后必须满足：

- `docs/` 只有上述 14 个 Markdown 文件，不含 archive、审查包、计划、handoff 或原始证据；
- `docs/design/` 恰好只有五份正式设计文档；
- 根目录 `plans/` 只含当前这轮尚未完成的 `-design.md` 和 `-plan.md`，完成收口后两者也退役；
- 技术栈、正式上线标准、技术问题与演进三项内容完整且各有唯一正本；
- `docs/技术难题/整库审查2026-07-26/` 及其他历史审查包不再留在工作树；
- 所有被保留内容描述当前事实，不依赖完成状态、旧 SHA、旧分支或一次性测试数字；
- 全仓不存在指向退役文档的有效引用；
- 文档相关测试和门禁验证真实意图，不通过固定文案保护旧结构；
- 客户端边界预算迁出 `docs/` 后，其检查器和测试仍通过；
- Git diff 不改变生产行为；如迁移路径必须修改脚本或测试，只允许等价的配套层改动；
- 所有退役内容均可从 Git 历史或 Trash 恢复，没有永久删除。

## 不做的事

- 不创建仓库内历史档案馆；
- 不为将来可能出现的文档提前建目录或模板；
- 不把所有脚本、测试或组件做成人工维护的清单；
- 不把已完成审查的结论逐条搬进新文档；只有仍影响当前行为或未来决策的内容才合并；
- 不借文档重构改变生产功能、视觉实现或发布策略。
